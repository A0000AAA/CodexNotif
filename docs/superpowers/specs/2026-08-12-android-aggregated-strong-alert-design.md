# Android 合并强提醒与后台铃声设计

## 背景

Android 客户端已经能够在后台收到匹配邮件并创建高优先级通知，但当前强提醒过度依赖系统通知声音和全屏通知调度。在小米 HyperOS 上，短时间内重复更新同一个通知会触发系统的“最近已响铃”静音策略；系统也可能只展示横幅而不启动全屏 Activity。结果是邮件已经匹配，通知可见，却没有持续铃声或全屏界面。

现有原生前台服务插件已经包含独立的循环音频播放器，并使用 `USAGE_ALARM` 音频属性。它不依赖 `MainActivity`，适合从后台 Flutter isolate 启停用户选择的铃声。

## 目标

- 第一封匹配邮件触发一次强提醒，循环播放用户选择的铃声，并尝试显示全屏提醒。
- 在用户确认前到达的后续匹配邮件合并进同一个提醒，不创建多个通知、不重复启动播放器、不重复抢占界面。
- 合并后标题显示“收到多封匹配邮件”，并显示累计数量和最新一封邮件的脱敏摘要。
- 用户从通知操作或全屏界面点击“我知道了”后，可靠停止铃声、取消通知并清空本轮合并状态。
- 前台服务停止或应用被用户从最近任务划掉时释放播放器，不保留幽灵铃声，也不恢复后台监听。
- 保留当前公开版的安全边界，不提交真实邮箱、服务器、密钥、设备标识、证书或本地绝对路径。

## 非目标

- 不恢复应用被划掉后的自动重启、开机自启或后台复活。
- 不保证所有 Android 厂商在所有锁屏状态下都允许 Activity 强制全屏；系统拒绝全屏时仍必须保留通知和持续铃声。
- 不为每封邮件创建独立提醒历史；本功能只聚合当前尚未确认的一轮强提醒。
- 不改变 IMAP 文件夹、匹配规则、UID 提交和邮件去重语义。

## 方案比较

### 方案一：后台原生播放器加单会话聚合（采用）

后台任务维护一个活动提醒会话。第一封邮件启动前台服务引擎中的原生循环播放器并创建通知，后续邮件只更新同一会话和同一通知。该方案不依赖 Activity 是否已经打开，能够避开系统通知重复响铃抑制，并能把停止动作统一收口。

### 方案二：仅依靠系统通知声音

实现改动较小，但会继续受 Android 和 HyperOS 的通知节流、勿扰策略、通知渠道缓存以及全屏调度限制影响，无法满足持续响铃要求。

### 方案三：仅在全屏 Activity 中播放

界面打开后体验直观，但系统不启动全屏 Activity 时播放器也不会启动，正好保留当前故障。因此不采用。

## 核心状态模型

后台 `MailMonitorTaskHandler` 持有一个可空的活动提醒会话，生命周期不跨前台服务进程：

- 固定通知 ID：继续使用当前强提醒通知槽位。
- `count`：本轮已合并的匹配邮件数量，初始为 `1`。
- `latestSender`、`latestSubject`、`latestMatchedRule`：只保存最新一封邮件用于当前界面展示。
- `soundUri`：本轮首次触发时确定的声音 URI；后续邮件不在响铃中途切换音源。
- `startedAt`：用于诊断和测试，不发送到服务器。

`StrongAlert` 传输模型增加向后兼容的 `count` 字段，缺失时按 `1` 处理。活动会话只存在于运行中的后台任务内，不写入公开配置，不在应用重启后恢复旧提醒。

## 触发流程

### 第一封匹配邮件

1. 邮件继续完成现有规则匹配和 UID 处理。
2. 创建 `count = 1` 的活动提醒会话。
3. 通过后台专用 MethodChannel 调用前台服务插件的原生播放器，循环播放会话中的 `soundUri`。
4. 创建一个高优先级、闹钟类别、带全屏 PendingIntent 的强提醒通知；通知本身不再重复播放系统声音，持续铃声只由后台原生播放器负责。
5. 只在这一刻执行一次小米后台弹出界面的最佳努力尝试；失败不能中断铃声或通知。
6. 把 `StrongAlert` 数据发送给主 isolate；若全屏页已被系统打开，则显示单封邮件内容。

播放器启动失败时，先尝试应用内置的可公开分发铃声；仍失败则保留可见通知，并记录不含 URI、邮箱或主题正文的错误类型。

### 后续匹配邮件

1. 增加活动会话的 `count`，并替换最新邮件摘要。
2. 不再次启动播放器，不再次请求全屏，不创建新通知 ID。
3. 静默更新现有通知，避免触发系统“最近已响铃”静音策略。
4. 标题精确显示“收到多封匹配邮件”；正文显示“共 N 封”以及最新一封的简短摘要。
5. 若全屏页仍打开，通过主 isolate 中现有会话控制器更新同一个页面，而不是再次入栈。

## 确认与清理流程

通知操作和全屏页中的“我知道了”必须走同一个确认命令：

1. 主 isolate 向后台任务发送 `acknowledgeStrongAlert`。
2. 后台任务停止原生循环播放器。
3. 取消强提醒通知并清空活动会话。
4. 关闭或更新已经打开的全屏页。

若后台任务已经不可用，主 isolate 仍通过后台音频通道直接停止同一个原生播放器，并执行取消通知和 Activity 播放器停止作为兜底。前台服务 `onDestroy` 必须无条件停止后台原生播放器，保证划掉应用后不继续响。

## 全屏策略

- 保留 Android 标准全屏通知作为跨厂商主路径。
- 在小米、Redmi、POCO 设备上，仅第一封且仅在用户已开启相应系统权限时，从前台服务上下文最佳努力启动提醒 Activity。
- 原生启动失败或被系统拦截时只记录结果，不降级为反复启动，也不影响通知和铃声。
- 后续合并邮件永远不重复弹出界面。

## 音频策略

- 后台强提醒使用前台服务插件中的 `AlertSoundPlayer`，音频属性保持 `USAGE_ALARM` 和循环播放。
- 后台原生播放器是强提醒唯一的音频源；全屏页只显示和确认，不再另外启动 Activity 中的提醒播放器，避免双重播放和相位叠加。
- 用户选择的本地或系统声音 URI 优先；打不开时回退到仓库允许公开分发的内置声音。
- 蓝牙 A2DP 已连接时由 Android 音频路由决定输出设备，不强制切换或独占蓝牙通话通道。
- 试听功能继续使用 `MainActivity` 的一次性播放器，与后台强提醒播放器相互独立。
- 同一活动会话不会因为通知内容更新而重启音频。
- 运行日志只记录启动、停止和错误类型，不输出声音 URI、邮箱地址、邮件主题或正文。

## 并发与失败处理

- 保留当前扫描互斥，避免两个 IMAP 扫描同时修改会话。
- 会话变更、通知更新和音频启停按后台任务事件顺序执行。
- 单封邮件处理失败不得增加计数；只有已经确认匹配并进入提醒流程的邮件才合并。
- 确认命令幂等：重复点击不会重新播放、报错或生成新通知。
- 前台服务停止清理也必须幂等。

## 测试设计

### Dart 单元与组件测试

- 第一封匹配邮件创建 `count = 1` 会话并只调用一次后台音频启动。
- 第二、第三封邮件复用固定通知 ID，计数递增，标题变为“收到多封匹配邮件”，且不重复启动音频或全屏。
- `StrongAlert` 对旧载荷缺少 `count` 的情况按 `1` 解析。
- 页面收到同一通知 ID 的更新时原位刷新，不重复压入路由。
- 从通知操作和全屏页确认都发送同一命令；重复确认保持幂等。
- 后台任务不调用仅由 `MainActivity` 注册的 `system_sound` 通道。

### Android 原生测试与静态验证

- 后台音频通道启动用户声音、失败时回退、停止时释放 `MediaPlayer`。
- 前台服务 `onDestroy` 调用音频清理。
- 小米最佳努力启动仅在第一封执行，异常不会阻断通知。
- Manifest 仍只保留已确认的必要权限，不新增短信、联系人、通话记录、定位、相机、麦克风或外部存储广泛权限。

### 小米真机验收

1. 冷启动应用并开启监听，切到桌面，保持应用任务存在。
2. 触发一封匹配邮件：验证通知、所选铃声持续播放、全屏或横幅至少出现一种。
3. 不确认，连续触发两封：验证只有一个通知，标题为“收到多封匹配邮件”，显示正确总数，铃声不中断也不重新开始。
4. 连接蓝牙音频设备重复测试，确认声音由系统路由到当前活动输出设备。
5. 点击“我知道了”：验证铃声立即停止、通知消失、再次点击无副作用。
6. 再触发新邮件：验证新一轮从单封、`count = 1` 开始。
7. 响铃时从最近任务划掉应用：验证监听停止且铃声立即释放，不自动恢复。

验收同时使用 `adb shell dumpsys notification`、进程/前台服务状态和精简日志确认通知 ID、全屏 PendingIntent、播放器启停及服务清理，不能只依据应用界面文字判断成功。
